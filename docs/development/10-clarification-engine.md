# 目标澄清引擎设计 v0.1

状态：首版实现基线已确认，承接产品文档 07；具体 schema 在代码初始化时用 Pydantic 和 OpenAPI 固化。

## 1. 模块职责

澄清引擎把用户消息转成“目标档案草稿 + 下一步决策”。它负责提取候选事实、识别缺口和矛盾、选择内部领域策略并决定是否可以进入档案确认。它不生成路线、不启用计划，也不能把模型推断直接标记为用户确认事实。

建议公开一个窄接口：

```python
evaluate_clarification(snapshot: ClarificationSnapshot) -> ClarificationDecision
```

`snapshot` 包含当前档案版本、最近用户消息、相关账号可用时间摘要、用户允许引用的现有目标摘要和策略版本。结果只返回候选变更，由应用服务校验并持久化。

## 2. 结构化结果

`ClarificationDecision` 至少包含：

- `profile_patch`：新增、修正或标记未知的档案字段。
- `evidence`：每项候选内容对应的消息引用和来源类型。
- `strategy_resolution`：内部领域、置信度、使用的策略版本和理由。
- `gaps`：缺口、严重程度、是否阻塞路线生成。
- `contradictions`：冲突字段及相互冲突的来源。
- `questions`：本轮零至三个相关短问题。
- `assumptions`：若继续规划将采用的可见假设。
- `readiness`：`needs_input`、`review_ready` 或 `blocked`。
- `split_proposal`：可选，建议拆分的结果及理由；不能自动创建额外目标。

模型只能返回允许的字段路径和枚举。账号 ID、目标 ID、已确认版本、时间预算和关联关系由服务端注入并校验，不能接受模型自行构造。

## 3. 处理流程

1. 应用服务保存用户原始消息并创建去重作业。
2. 读取目标、档案草稿、账号时间设置和允许的少量上下文，形成带 revision 的快照。
3. 规则层先找出确定性缺口，例如尚无时间预算或存在字段冲突。
4. 模型提取语义、提出候选修正、内部策略路由和高价值问题。
5. Pydantic 校验结构；规则层重新计算缺口、阻断项和 readiness，不能直接信任模型结论。
6. 提交前检查 revision；输入已变化则结果标为 stale，重新评估。
7. 保存档案草稿修订、来源、问题和可见假设，并通过作业事件通知前端。

模型调用在数据库事务外进行。相同消息与相同档案 revision 使用稳定去重键；重试可以增加模型费用，但只能提交一个有效草稿修订。

## 4. 字段与来源规则

每个档案字段保存值、来源消息、来源类型和确认状态。来源类型建议为 `user_stated`、`agent_inferred`、`user_accepted_assumption` 和 `unknown`。用户在档案页确认后形成不可变 `goal_profile` 版本；此前内容都只是草稿。

用户明确修正旧事实时，新值引用旧值并标记为 superseded，不能静默改写历史消息。Agent 推断必须显示在假设区域；用户接受后才转换为已接受假设。未知值不是空字符串，也不能在提示中被默认补全。

## 5. 防止无休止追问

问题生成受服务端规则约束：每轮最多三个、不得询问内部领域、不得询问已存在且没有冲突的事实。连续两轮后，若只剩非阻塞缺口，服务端强制 readiness 至少达到 `review_ready`，由页面展示假设和待补项。

如果模型反复生成相同问题，按规范化 question key 去重并要求重新生成一次；仍无有效问题时进入档案检查页或返回可解释的阻断原因，不能无限调用模型。

## 6. API 衔接

- `POST /api/goals` 只接收初始描述，创建 draft 目标、对话与 planning session。
- `POST /api/conversations/{id}/messages` 保存补充内容并返回澄清作业。
- `GET /api/goals/{id}/profile-draft` 返回当前草稿、来源、缺口、假设、矛盾和 readiness。
- `PATCH /api/goals/{id}/profile-draft` 接收用户直接编辑及 expected_revision。
- `POST /api/goals/{id}/profile-confirmations` 在服务端重新检查阻断项后创建不可变档案版本。

只有已确认档案的 ID 可以用于路线生成。关键档案修改后，基于旧版本的路线集合和计划草稿显示 stale，但已启用计划在新版本正式应用前继续有效。

## 7. 测试重点

- 同一句自然描述在固定模型输出下得到稳定字段映射和来源。
- 已有账号时间设置不会被模型问题重复索取。
- 模型声称 `review_ready` 但缺少结果定义时，被规则层拒绝。
- 用户修正期限后，旧值保留来源但不参与当前路线输入。
- 两次相同提交只产生一个有效草稿修订。
- 作业运行时用户编辑档案，旧模型结果不能覆盖新 revision。
- 领域置信度低时使用通用策略，不生成领域选择问题。
- 第二轮后只剩偏好缺口时进入档案检查，而不是继续追问。
