# 开发流程与决策规程

本文定义从需求到合并的完整路径，以及"谁有权把一件事定下来"。目标是让开发者各自借助 AI 工具并行工作而不产生互相不兼容的结果。

## 1. 文档分层与事实源

| 层 | 位置 | 回答什么问题 | 谁可以改 |
| --- | --- | --- | --- |
| 术语 | `CONTEXT.md` | 我们在说的是同一件事吗 | 全员评审后改 |
| 产品 | `docs/product/` | 要解决什么问题、验收标准是什么 | 产品决策人 |
| 设计 | `docs/development/` | 怎么实现、模块边界与契约在哪 | 对应模块负责人 |
| 提案 | `docs/rfcs/` | 要改变一个已确认的决策 | 任何人提，负责人批 |
| 任务 | `docs/worklog/` | 这个工作包当前做到哪、有哪些假设 | 工作包负责人与其 AI |
| 代码 | `backend/` `frontend/` | 最终行为 | 按 CODEOWNERS |

**下层不得推翻上层。** 代码与设计冲突，先改设计再改代码；设计与产品冲突，先走 RFC。

## 2. 结论的三种状态

设计文档里的每个结论必须可判断状态，写法见 [AGENTS.md](../../AGENTS.md) 的"文档状态标记"。

- **已确认**：可以直接实现，偏离需要 RFC。
- **建议 / 推荐**：设计稿给出的默认值，**实现前必须确认**。
- **待定 / 未决**：没有结论，遇到即停。

这一条是本规范里最容易被违反、后果最大的一条。现有设计文档仍有"建议""待定"标注（例如 `06-delivery-plan.md`"当前需先收敛的事项"里的 OpenAI / Anthropic API 子集、`docs/worklog/T01-sqlite-verification.md` 第 9 节尚未决的事项），AI 读到这些内容时会倾向于自动补全成一个看起来合理的实现。必须按下面的规程处理。

反过来同样要注意：一个结论被收敛为"已确认"后，引用它的其他文档必须同步改状态。漏改会让下一个 AI 会话把已定的事再当成待定停下来，或者重新走一遍 RFC。

## 3. 决策规程：把"建议"变成"已确认"

遇到未决项时，按影响范围选择路径：

| 影响范围 | 路径 | 产出 |
| --- | --- | --- |
| 只影响单个工作包内部实现 | 工作包负责人自行决定 | 记入该工作包交接卡的"决策与假设" |
| 影响公共契约、数据模型、跨模块行为 | 提 RFC，模块负责人批准 | `docs/rfcs/NNNN-*.md` + 同步更新对应设计文档 |
| 改变产品行为或验收标准 | 产品决策人确认 | 更新 `docs/product/` 并把状态改为"已确认" |

**任何情况下都不允许沉默地选一个默认值继续写代码。** 至少要在交接卡里写成显式假设，让下一个人和下一个 AI 会话看得见。

RFC 合并后必须回写到对应设计文档，把状态从"建议"改为"已确认"。设计文档正文只保留最终结论，不保留演进过程——过程留在 RFC 与 Git 历史里。

## 4. 角色（2–3 人规模）

人数不足时一人兼多顶帽子，但**同一时刻每顶帽子只有一个人**：

| 帽子 | 负责范围 | 对应工作包 |
| --- | --- | --- |
| 后端与数据 | 数据模型、迁移、账号会话、作业与恢复 | T01、T03、T04、T07 |
| 业务规则 | 排期、时间预算、目标关联、依赖与冲突 | T05、T06、T12 |
| Agent 与模型 | LangGraph 步骤图、领域策略、LangChain 模型接入 | T08、T09、T14 |
| 前端 | 页面、状态、契约消费 | T10、T11 |
| 集成与交付 | 工程基础、公共契约、部署与发布 | T02、T13、T15 |

**公共契约由"集成与交付"这顶帽子单点维护**，其他人通过 RFC 或 Issue 请求变更，不直接改。谁戴哪顶帽子记录在 `.github/CODEOWNERS`。

## 5. 单个任务的完整路径

```text
选工作包 → 建交接卡 → 对齐契约 → 建分支 → 实现 → 自检 → 提 PR → 评审 → 合并 → 收尾交接卡
```

1. **选工作包**：从 `06-delivery-plan.md` 的 T01–T15 里选一个依赖已满足的。里程碑 M0（T01 数据库行为验证 + T02 工程契约基础）未完成前，不要开工依赖它的任务。
2. **建交接卡**：复制 `docs/worklog/TEMPLATE.md` 为 `docs/worklog/T05-scheduling.md`，填写范围、可改路径、输入契约、验收场景。**这一步在写代码之前完成**，它同时就是给自己 AI 的任务说明书。
3. **对齐契约**：如果任务需要新增或修改接口、枚举、错误码、表结构，先单独提一个契约 PR 合并，再开始实现。契约未定就并行实现，是多人 AI 开发最主要的返工来源。
4. **建分支**：`<类型>/T<NN>-<简述>`，从最新 `main` 切出。
5. **实现**：AI 会话按 [AI 协作规范](02-ai-collaboration.md) 启动。每完成一个可验证的小步就提交一次，不要攒成一个巨大提交——AI 单次输出量大，攒起来的提交没人能真正审。
6. **自检**：`bash scripts/check.sh` 与 `bash scripts/test.sh` 全绿，对照 [完成定义](04-definition-of-done.md) 逐条核。
7. **提 PR**：按模板填写，特别是**实际执行过的验证命令**和 **AI 使用声明**。
8. **评审**：见下节。
9. **合并**：squash merge 到 `main`，提交信息用 PR 标题。
10. **收尾**：更新交接卡的"已完成""验证结果""未决问题"，让它对下一个接手的人或会话可用。

## 6. 评审规则

| 变更类型 | 要求 |
| --- | --- |
| 公共契约（OpenAPI、迁移、共享枚举与错误码） | **必须**由契约负责人以外的至少 1 人批准，不得自审自合 |
| 跨模块行为、排期规则、权限与数据隔离 | 必须他人批准 |
| 单模块内部实现、测试、文档 | 可自审，但 CI 全绿是硬前提，且需在 PR 里写明自审理由 |
| 纯文案、样式、注释 | 可自审自合 |

人手紧张时可以放宽"他人批准"的时效，但**不得放宽 CI 门禁**。CI 是这套流程里唯一不依赖人力的质量下限。

评审关注点见 [完成定义与评审清单](04-definition-of-done.md)。

## 7. 分支与集成

- `main` 为唯一长期分支，始终保持可运行、CI 全绿。
- 功能分支生命周期尽量短，超过一周未合并必须先 rebase 到 `main` 并说明原因。
- 禁止直接向 `main` 推送，全部通过 PR。
- 不使用长期存在的 `develop` 分支——2–3 人规模下它只会增加合并冲突面。

## 8. 里程碑门

`06-delivery-plan.md` 定义的 M0–M4 是**门**，不是进度标签。前一个门未达成，不得声称后一阶段完成：

- **M0** 技术基础可验证：T01、T02 完成，数据库不支持项与采用的替代实现已明确记录，公共契约稳定。
- **M1** 业务链路可运行：账号、草稿、预算、去重、执行记录可用；使用模拟模型时必须在界面和交付说明中明确标识。
- **M2** 真实规划闭环：从表达目标到启用计划再到第一条反馈可走通。
- **M3** 多目标与调整完整：隔离、关联、冲突、确认、记录更正、回顾通过。
- **M4** 可发布试用版：真实环境部署、注册登录、恢复、数据隔离、模型链路验证完成。

M1 是内部检查点，**单目标样例通过不能替代多目标交付**。
