# AI 协作规范

本项目默认每位开发者都在用 AI 编码工具，且工具不统一（Claude Code、Codex、Cursor 等）。本文解决的问题是：**让不同的人、不同的工具、不同的会话，在同一个仓库里产出可以合并的结果。**

核心思路：把上下文外置到仓库里。AI 的会话记忆会消失，人的记忆会衰减，只有仓库里的文件是共享且持久的。

## 1. 会话启动清单

每个新的 AI 编码会话开始时，按顺序给它以下输入。**不要跳过第 4 步**，它是范围失控的唯一防线。

1. **仓库指南**：`AGENTS.md`（Claude Code 经 `CLAUDE.md` 自动加载；其他工具手动指定）。
2. **术语**：`CONTEXT.md`。
3. **任务上下文**：当前工作包的交接卡 `docs/worklog/T<NN>-*.md`，以及它引用的设计文档。
4. **边界**：明确说出本次可修改的路径，以及明确不可修改的路径。例如：

   > 本次只能修改 `backend/src/goalflow/scheduling/` 和 `backend/tests/scheduling/`。
   > 不要修改 `openapi/`、`backend/migrations/`、`backend/src/goalflow/contracts/`、前端任何文件。
   > 需要改这些的话先告诉我，不要自己动手。

5. **当前状态**：`git status` 与 `git log --oneline -5` 的输出，让它知道自己接的是什么现场。

会话中途目标发生变化时，先更新交接卡再继续，不要只在对话里改口——对话不会留下来。

## 2. 交接卡（Handoff）

交接卡是本规范里唯一强制新增的产物，位于 `docs/worklog/T<NN>-<slug>.md`，模板见 [TEMPLATE.md](../worklog/TEMPLATE.md)。

它要回答四个问题：

- **要做什么**：范围、可改路径、验收场景。
- **依据什么**：输入契约、引用的设计文档与其状态标记。
- **已经决定了什么**：决策与假设，尤其是把"建议"收敛成具体值的那些选择。
- **还剩什么**：进展、验证结果、未决问题、给接手者的说明。

### 什么时候必须写

- 领取工作包时创建（**写代码之前**）。
- 任何一次会话结束、上下文即将丢失、或要交给别人之前更新。
- 做出一个会影响别人的决定时，立刻记入"决策与假设"。
- PR 合并后收尾。

### 为什么它值得这点成本

没有交接卡时，典型情况是：A 用 AI 做完 T05 的一半，三天后 B 接手，B 的 AI 从零开始读代码猜意图，把 A 已经排除过的方案又试一遍，或者把 A 显式选定的默认值改掉。交接卡把"为什么是这样"写下来，让第二个会话不必重新推导。

交接卡是**当前状态**的描述，不是日志。更新时直接改写成最新状态，不要追加"第二次会话：……"这样的流水账。真正的历史在 Git 里。

## 3. 任务粒度

AI 单次可以产出很多代码，但**可审的代码量没有变大**。控制粒度：

- 一个 PR 对应一个可独立验收的能力，目标控制在 400 行有效改动以内（生成物与锁文件不计）。
- 超过这个量级就拆分：先契约，再核心规则，再接口层，再页面。
- 每个能通过 `scripts/check.sh` 的中间状态就提交一次。

不要让 AI 一次性生成一整个工作包。T04、T05、T08 这类工作包本身就应该拆成多个 PR。

## 4. 验证责任

**AI 生成的代码，责任在提交它的人。** 这条没有例外。

- 报告"测试通过"前必须真的运行过并保留输出。PR 里的验证命令列表应当是复制粘贴的真实记录，不是理论上应该运行的命令。
- AI 写的测试要人工看一遍：它容易写出"镜像实现"的测试——把实现里的常量抄到断言里，实现错了测试也跟着错。判断标准是：**如果实现有 bug，这个测试会失败吗？**
- AI 引用的库 API、配置项、命令行参数可能过时或虚构。涉及 seekdb、Celery、Alembic、模型 SDK 的用法，以官方文档为准。
- AI 给出的性能、兼容性、安全性结论，在没有实测支撑前只能当作假设，记入交接卡而不是写进设计文档。

## 5. 上下文卫生

- **不要把整个仓库塞进上下文。** 给相关设计文档和目标模块，其余让工具自己检索。
- **不要依赖跨会话记忆。** 任何需要被下次用到的结论，写进交接卡或 RFC。
- **不要让 AI 把 `docs/` 之外的猜测性内容当作需求。** 聊天记录、群里的讨论不是需求，PRD 才是。
- 会话变长、AI 开始重复或偏离时，重启会话并用交接卡重新加载，比继续纠正更省时间。

## 6. 多人多 AI 并行时的冲突规避

- **开工前先看别人在做什么**：`docs/worklog/` 下有哪些卡处于进行中，避免两个人的 AI 同时改同一模块。
- **公共契约串行**：契约变更同一时间只允许一个在途 PR，第二个人等合并后 rebase。
- **迁移串行**：同一时间只允许一条新增迁移在途，由数据负责人排序。
- **生成物不要手工解冲突**：`frontend/src/shared/api/generated/`、锁文件出现冲突时，取 `main` 的版本后重新生成或重新安装，不要逐行合并。
- **长分支定期 rebase**：AI 在过时基线上工作会生成基于过时契约的代码，越晚发现代价越大。

## 7. 禁止项

以下行为在本项目中不可接受，重复出现按流程问题处理而非个人失误：

| 禁止 | 原因 |
| --- | --- |
| 未运行就声称测试通过 | 直接污染团队对当前状态的判断 |
| 把"建议 / 待定"实现成既成事实且不记录 | 后续无法区分哪些是产品决策、哪些是 AI 猜的 |
| 手工编辑生成物 | 下次生成即被覆盖，且掩盖真实契约 |
| 顺手修改工作包范围外的文件 | 评审面扩大、冲突增加、责任不清 |
| 为了让测试通过而改测试断言 | 掩盖真实缺陷 |
| 提交含真实凭证的代码或配置 | 安全事故；本项目要处理用户的模型 API Key |
| 用 `# type: ignore`、`any`、`!` 批量消除类型错误 | 把问题从 CI 转移到运行时 |
| 删除或弱化既有测试来让 CI 变绿 | 同上 |

## 8. AI 使用声明

每个 PR 必须填写 AI 使用声明，写明工具与模型，例如"Claude Code / Opus，生成排期规则与测试，人工复核并修正了边界条件"。未使用则写"未使用"。

这不是为了追责，而是为了判断评审强度：大量 AI 生成且作者对细节把握不深的 PR 需要更仔细的人工审查，尤其是并发、事务和权限相关的部分。

## 9. 工具配置

| 工具 | 读取入口 | 说明 |
| --- | --- | --- |
| Claude Code | `CLAUDE.md` → `AGENTS.md` | 自动加载 |
| Codex / Cursor / 其他 | `AGENTS.md` | 约定入口，会话开始时手动指定 |

**规则只写在 `AGENTS.md` 一处**，其他文件只做指向。如果某个工具需要特殊配置，在本文追加一行说明，不要复制一份规则出去——两份规则一定会发散。
