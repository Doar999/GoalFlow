# 方案预览与选择 v0.2

状态：首版产品方案已确认，包括路线数量、比较字段、有条件推荐和微调边界。

## 已确认

先展示几份完整方案供用户比较，用户选择一份后再微调，随后生成可执行计划。用户无需先配置大量参数。

保留执行前检查：生成计划后展示计划总览与首周安排，用户点击“开始执行”后才正式启用并进入今日执行页。选定路线不等于启用计划。

## 路线与计划的边界

路线用于比较“采用什么总体方法、需要怎样投入、要接受什么取舍”，计划用于回答“分哪些阶段、具体做哪些任务”。路线可以展示阶段轮廓和示例任务，但不提前生成全部任务，也不进入今日页。

同一组路线必须基于同一份已确认目标档案。改变成功标准、目标范围或硬期限的候选不能伪装成普通路线，应单独显示为“调整目标约束后的备选建议”。

## 数量与生成原则

此处完整方案指足以判断取舍的整体路线，包括预计周期、每周投入、执行方式、阶段成果、主要难点和对其他目标时间预算的影响；不提前生成全部远期每日任务。

建议默认最多展示三份路线：存在三种真实取舍时展示三份，只有两种可行路径时展示两份，约束只允许一种时展示一份并说明原因。不能为了凑数改写标题或文案。

不固定套用“轻松、均衡、冲刺”。候选差异从目标本身推导，可以来自方法、节奏、阶段顺序、反馈频率、资源使用、风险控制或不确定性处理。每条路线必须声明至少一个与其他路线不同、且会影响用户执行体验或结果风险的关键决策。

## 统一比较字段

| 字段 | 用户需要理解的内容 |
| --- | --- |
| 路线核心 | 主要方法以及为什么适合当前目标 |
| 预计周期 | 使用范围或阶段估计，不伪装成精确承诺 |
| 时间投入 | 各阶段每周预计分钟数、峰值投入和与共享预算的缺口 |
| 阶段成果 | 每个阶段可观察的结果，不展开全部每日任务 |
| 验证方式 | 如何判断正在进步，以及何时需要改变路线 |
| 主要取舍 | 这条路线获得什么、牺牲什么 |
| 风险与假设 | 依赖的未知信息、资源和可能失败点 |
| 其他目标影响 | 占用共享时间后，对现有目标造成的冲突或余量 |

所有路线使用相同字段和单位。页面先显示最关键差异，再允许展开详情；不能用总分隐藏取舍。

## 推荐规则

系统可以推荐一条路线，但必须先通过硬约束和共享时间预算校验。推荐依据按顺序为：用户明确偏好、目标成功标准、可用投入、既有目标冲突、领域风险和不确定性。推荐理由应指出具体匹配关系，例如“满足每周 180 分钟上限且保留两次复习”，不能只说“更适合你”。

当信息不足以形成明显推荐时，明确标记“没有唯一推荐”，交由用户比较。首版不展示模型生成的成功概率或伪精确评分。

## 交互建议

1. 从已确认目标档案、内部领域策略和共享时间预算生成一个路线集合。
2. 用统一字段并列比较，突出决定性差异，展开查看阶段轮廓及示例任务。
3. 系统可以给出带理由的推荐；用户选择任意路线或表示都不合适。
4. 选择后通过对话或直接控件微调，例如降低工作日投入或增加验证频率。
5. 重新检查成功标准、期限、领域约束和其他目标占用，展示修改前后差异。
6. 用户确认路线后生成计划草稿。生成失败时保留已选路线及微调内容，允许重试。
7. 用户检查计划，可以提出修改或返回调整路线；点击“开始执行”后才启用计划并进入今日执行页。

微调如果只改变允许范围内的投入分配、反馈频率或阶段节奏，就基于原路线创建新版本并重新校验。修改核心方法、成功标准、硬期限或关联目标时，旧路线集合标记为过期，并重新生成可比较路线。

## 执行前检查的细则建议

- 总览展示目标成功标准、阶段里程碑、预计周期、每周投入及关键假设；首周展示每日任务与合计用时，以及其他目标占用后的剩余预算。
- 草稿不加入正式每日清单、不触发执行提醒、不占用正式排期预算；预览仍需使用现有预算评估可行性。
- 开始执行前重新检查开始日期、预算、任务依赖与关联目标影响。草稿放置后日期过期或资源变化时，展示更新差异并由用户确认，不静默启用失效安排。
- 启用操作应避免重复提交造成重复任务；失败时保留草稿并说明状态。
- 首周已确认按开始日起连续七个本地日期展示；今天有容量则默认今天，否则选择下一个可用日期，用户可以修改。

## 约束建议

- 用同一目标及成功标准比较路线。若某路线需要修改目标范围或期限，单独标明为变更建议，需用户确认后采用。
- 周期和投入是基于现有信息的估计，展示重要假设，不编造精确成功概率。
- 没有多条可行路线时说明原因，不凑数；所有路线不可行时返回冲突澄清。
- 用户可以表示均不合适并说明原因，保留既有信息生成新路线。
- 预览或微调不改变现有活跃计划；确认前重新校验时间预算，防止比较期间其他目标已经发生变化。
- 选定路线也不自动授权改变其他目标；涉及关联目标的重大影响仍需确认。

## 不可行与失败处理

- 部分候选不可行：只展示通过校验的路线，并说明为什么少于三份。
- 只有一条可行：展示该路线和约束原因，同时提供用户能够调整的条件。
- 全部不可行：不生成看似完整的路线，返回时间、期限、资源或依赖冲突，以及可以修改的杠杆。
- 模型输出结构错误或路线重复：自动修复一次；仍失败则保留档案和作业错误，允许重试或更换模型。
- 生成期间目标档案或时间预算变化：结果标记为过期，不能覆盖新的路线集合。

## 验收场景

- 三条路线只改标题、阶段和投入基本相同时，差异校验拒绝该集合。
- “低投入路线”暗中降低成功标准时，不进入同组比较，而是作为目标约束调整建议。
- 每周只剩 120 分钟时，预计需要 240 分钟的路线显示明确缺口，不能被推荐为可行。
- 用户将每周投入从 180 分钟微调为 150 分钟后，系统展示周期或阶段变化并重新校验。
- 生成过程中另一个目标占用了共享时间，旧结果显示过期，重新评估后才能选择。
- 没有明显最佳路线时，系统不强制推荐。
