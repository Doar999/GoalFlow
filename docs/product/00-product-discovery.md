# 产品探索草案

> 状态：讨论中（v0.6）
> 本文记录已经提出的产品方向、当前假设和待确认问题，不代表最终需求。

## 一句话定义

一个围绕用户目标持续工作的 Agent：它通过对话理解目标，提供多种执行路线供用户选择，将路线转化为可执行计划，并根据每日执行反馈持续安排任务和调整计划。

## 当前要解决的问题

用户通常不只缺少一份计划，还会遇到以下问题：

- 目标描述模糊，不知道真正要达成什么结果。
- 可行路线很多，不知道应该选择多快、多难或多激进的方式。
- 有了计划仍不知道今天具体该做什么。
- 执行过程中会遇到延期、阻碍和目标变化，静态计划很快失效。
- 缺少持续反馈，无法判断自己是否真的接近目标。

## 核心闭环

1. **目标澄清**：通过对话识别目标、动机、期限、约束、资源与成功标准。
2. **路线预览**：从节奏、投入、风险、灵活性等维度生成若干可比较的路线。
3. **路线选择**：已确认先展示几份完整路线供用户比较，再选择并微调。详见 [方案预览与选择](03-route-selection.md)。
4. **计划生成与启用**：生成包含阶段、里程碑、任务依赖和验收标准的计划草稿。已确认保留计划总览与首周安排检查，用户点击“开始执行”后正式启用。
5. **每日安排**：根据计划、用户当天可用时间及前序完成情况生成今日任务。
6. **执行记录**：用户提交完成情况、产出证据、耗时、困难和主观感受。
7. **评估与调整**：Agent 判断是否保持计划、调整任务、重新规划或与用户确认目标变化。

## 需要区分的产品对象

- **目标（Goal）**：用户希望达成且可以判断是否完成的结果。
- **路线（Route）**：达成目标的一种总体策略，用于选择节奏和取舍。
- **执行计划（Plan）**：选定路线后生成的、可版本化调整的阶段与任务结构。
- **每日安排（Daily Agenda）**：面向未来或当天的行动清单。
- **任务（Task）**：具有明确动作、完成标准、预计投入和计划时间的执行单元。
- **执行记录（Check-in）**：用户对实际执行结果的反馈，包括证据、阻碍和状态。
- **计划调整（Plan Revision）**：依据执行记录产生的计划变更。

每日安排和执行记录可以在界面中呈现为同一条时间线，但在产品与数据模型中应分别保存：前者表达“准备做什么”，后者表达“实际发生了什么”。

## 当前关键假设

- Agent 的价值来自持续执行闭环，而不只是一次性生成计划。
- 用户应能理解不同路线之间的实际取舍，而不是面对几份文字相似的方案。
- 计划需要保留版本和调整原因，否则用户无法理解任务为何变化。
- 每个目标必须存在可检查的成功标准；否则 Agent 只能推动活动，不能判断进展。
- 已确认首版支持学习、健身、通用三类，落实专属澄清问题、任务类型和反馈规则；项目交付先归通用场景，具体规则见 05-domain-scope.md。

## 待确认的核心问题

1. 首版面向个人用户并允许直接注册；三类范围已确认，具体试用样例与验证规则待细化。
2. 首版应用内辅助工作的具体清单，以及资料检索的数据来源和成本边界。
3. 已确认轻量记录为主、关键任务再验证；各领域验证标准和材料支持范围待细化。
4. 已确认小调整自动执行、大调整需确认；可移动日期范围与投入变化阈值待细化。
5. 用户每天需要投入多少交互成本，产品如何避免提醒疲劳和计划压力？
6. 多目标共享时间预算下的优先级、最低投入和冲突处理规则如何设定？

## 候选 MVP 边界

已确认：首发平台为网页端。建议采用响应式布局，电脑端支持完整规划与执行，手机浏览器便于查看任务和提交反馈；具体移动端覆盖范围待细化。当前阶段继续完善产品与开发文档，尚未开始应用实现。

已确认：首版是面向个人用户、开箱即用的开源产品，提供无需邀请码的注册登录。同一实例的用户数据相互隔离。账号、用户数据隔离与费用控制见 [开源产品与用户范围](04-open-source-product.md)。

已确认：首版提供规划、指导、复盘和应用内辅助工作；后续接入扩展能力。应用内辅助工作的候选包括资料搜集、练习题生成、内容解释和研究结果整理。资料搜集需要真实检索能力和可追溯来源，不能将模型生成内容当作已检索资料。

已确认：第一版允许同时推进多个目标。用户可选择目标独立推进或与指定目标关联；独立目标的计划与任务相互独立，所有目标仍统一协调用户时间。详细规则见 [多目标协调](02-multi-goal-coordination.md)。

仍为建议：第一版每个账号独立管理个人目标，不提供多人共同编辑目标。已确认默认最多展示三条有实际取舍差异的路线，有几条可行就展示几条，并且只在存在明确依据时推荐。活跃目标数量上限和阶段复盘频率尚未确定。已确认每天提供一次可跳过的简短回顾。外部系统写入、多人协作和复杂第三方集成留待后续。

## 首版执行原则（建议，细则待确认）

已确认首页采用今日执行页。页面结构及状态处理建议见 [今日执行页](01-today-page.md)。
首版按日展示任务与预计总时长，不自动安排具体时刻；未来支持每日清单与具体时段模式切换。

- 目标形态区分达成型与维持型；后者按周期评估持续状态，不强制设置完成日期。
- 已确认：澄清采用 LLM 语义理解与 Python 规则判定相结合的方式。每轮优先提出一个问题组，最多包含三个相关的关键问题；支持不知道、跳过非关键项和短期诊断。关键缺口无法评估时，先提供诊断任务而非承诺结果。
- 目标档案区分用户事实、Agent 建议和未确认假设；成功标准需用户认可。
- 对期限、投入与范围的冲突显式展示取舍，不擅自缩减目标。
- 采用滚动规划：整体阶段明确，近期安排细化，远期任务随反馈逐步展开。
- 分别评估执行情况与目标结果；打卡完成率不直接代表目标进度。
- 未反馈不等于未完成；中断后先了解现状，不自动累积所有过期任务。
- 已确认：以计划包络作为自动调整边界；包络内的小幅任务和排期调整自动进行并说明原因，越过投入、日期、里程碑、成功标准、锁定或目标关系边界需用户确认。不覆盖已完成记录，不擅自替换进行中任务。连续两次摩擦触发诊断，至少三条可比记录后再校准估算。
- 日志时间线同时呈现每日安排、实际反馈和调整原因，保留历史记录。

## 扩展能力边界（开发设计建议）

领域策略决定如何规划和评估；执行能力决定 Agent 能实际完成哪些操作，两者独立演进。首版内置辅助能力，后续通过统一能力接口接入外部工具，无需首版建设完整插件平台。

- 每条任务标识由用户执行、Agent 执行或双方协作；Agent 完成辅助产物不能自动代表用户完成学习或训练。
- 规划前检查可用能力，不生成依赖尚未接入工具的自动执行承诺。
- Agent 执行记录包含请求、状态、产物或来源及失败原因；失败时明确反馈，提供重试或用户接手路径。
- 后续扩展能力声明输入输出、授权范围与外部影响；授权、撤销及重复执行处理在接入具体工具时细化。

## 通用内核与领域策略

产品采用“统一目标生命周期 + 领域策略”的模型。

所有目标共享目标澄清、路线比较、计划生成、每日安排、执行记录、评估调整和目标结束这条生命周期。不同领域不复制生命周期，而是在各环节提供专属的问题、规则、任务类型、进度指标和调整方法。

按最新确认，内部领域策略包含学习、健身、通用三类，但不向用户提供必选分类步骤。Agent 根据目标描述与后续事实自动选择策略；通用承载基础和兜底规则，学习与健身增加专属规则。项目交付先作为通用类场景，下面的项目交付列用于展示场景差异，不代表首版独立类别。

| 环节 | 学习领域侧重 | 健身领域侧重 | 项目交付领域侧重 |
| --- | --- | --- | --- |
| 目标澄清 | 当前水平、目标能力、考试/应用场景 | 身体基础、健康限制、目标指标 | 交付物、期限、质量标准、利益相关方 |
| 路线比较 | 课程路径、练习密度、测评方式 | 训练强度、恢复要求、饮食配合 | 范围、速度、质量、成本与风险 |
| 计划结构 | 知识依赖、学习单元、复习周期 | 训练周期、渐进负荷、恢复周期 | 阶段、里程碑、依赖、关键路径 |
| 每日任务 | 学习、练习、复习、测试 | 训练、饮食、恢复、测量 | 制作、验证、沟通、解除阻碍 |
| 进度证据 | 测验成绩、作品、应用表现 | 训练记录、身体指标、主观疲劳 | 已完成交付物、验收结果、阻碍状态 |
| 调整依据 | 掌握度和遗忘情况 | 完成率、恢复状况和安全限制 | 进度偏差、范围变化、依赖与风险 |

## 目标分类原则

- Agent 根据用户描述与已确认事实推断一个**主领域**，作为内部工作流路由，不要求用户确认或修改分类。
- 目标可以包含多个**次要特征**，用于补充计划规则，但只有一个主领域负责整体规划。
- 领域判断置信度不足时，先使用通用策略继续澄清；只询问会影响方案的目标事实，不询问用户“属于哪一类”。
- 分类不是永久标签；当目标事实变化时，Agent 可以迁移领域策略并记录原因。若迁移导致已启用计划发生重大变化，仍按计划变更规则请求确认，但不要求用户确认分类本身。

示例：“三个月内做出并发布一个英语学习 App”首版归入通用类的项目交付场景；英语学习是产品主题，不代表该目标属于学习类。如果用户需要补齐移动开发知识，可在计划中提出学习任务建议。

## 领域策略需要提供的内容

每个领域策略至少定义：

- 目标澄清所需字段和追问规则。
- 成功标准及可接受的进度证据。
- 路线生成时必须展示的取舍维度。
- 计划阶段、任务类型和依赖规则。
- 每日任务编排与工作量估算规则。
- 执行反馈的评估方式。
- 自动调整边界和必须征求用户意见的变化。
- 领域风险、安全限制及禁止建议。
