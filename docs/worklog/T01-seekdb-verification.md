## 1. 目标

在真实 seekdb 实例上验证 [核心数据模型](../development/03-data-model.md) 所依赖的数据库行为，产出三样东西：一套可重复运行的验证套件、一张逐项结论表、以及每个不支持项所采用的替代实现。

达成标准：结论表无空项；红线项全部通过；所有"不支持/部分支持"项都已写明替代实现并回写到对应设计文档。M0 门以此为前提。

**本工作包不实现业务表，也不产出生产 DDL。** 它只回答"这个数据库能不能承载已设计的协议"。

## 5. 验证用例清单

每条用例都必须是可重复运行的自动化测试，并在结论表中填入：支持 / 部分支持 / 不支持、实测值、采用的替代实现。

### A 连接与工具链

- [ ] **A1** PyMySQL 驱动连接 seekdb Server，SQLAlchemy 2 MySQL 方言建连、查询、关闭正常
      _不支持 → 换 mysqlclient；两者均不可用则阻断并走 RFC_
- [ ] **A2** `inspect()` 反射表、列、索引、唯一约束、外键，结果与建表语句一致
      _反射不全 → 放弃 Alembic autogenerate，全部手写迁移；须回写工程规范，因为它改变契约 PR 的工作量_
- [ ] **A3** Alembic upgrade 与 downgrade
      _downgrade 不可用 → 迁移只向前，回滚依赖备份恢复加人工说明_
- [ ] **A4** 连接池断连重连与 `pool_pre_ping`
      _不生效 → 显式重试包装_

### B 类型与物理存储

- [ ] **B1** CHAR(36) 存 UUID 并建唯一索引，等值查询正常
      _不适用 → 改 BINARY(16) 加应用层转换_
- [ ] **B2** DATE 业务日期无时区偏移，跨日边界正确
      _不适用 → 存 INT(YYYYMMDD)_
- [ ] **B3** DATETIME(6) 写入读回保留微秒
      _不支持 → 降级到秒，排序改依赖 `job_events.sequence`_
- [ ] **B4** JSON 列类型写入、读回，记录长度上限实测值
      _不支持 → LONGTEXT 存序列化 JSON 加应用层校验；成本低，已确认不使用 JSONB 语法_
- [ ] **B5** 长文本字段实测可存最大长度（instructions、note、summary，以及验证材料的 20 万字符抽取文本）
      _低于需求 → 分段存储，或下调文档 10 的字符上限并回写_
- [ ] **B6** 按计划列宽建立全部唯一索引，确认 utf8mb4 下的索引长度限制
      _超限 → 缩短列宽或改前缀索引。**必须在建表设计定稿前测**，否则迁移会在中途失败_

### C 约束与唯一性

- [ ] **C1（红线）** 复合唯一约束生效：`(goal_id, version_no)`、`(owner_id, kind, dedupe_key)`、`(agenda_id, version_no)`、`(owner_id, local_date)`、`(job_id, sequence)`
      _失败 → 去重机制失去地基，走 RFC_
- [ ] **C2** 唯一冲突异常可稳定识别为"唯一键冲突"，且能区分是哪个键
      _无法区分具体键 → 改先查后插加事务内重试，需评估引入的竞态_
- [ ] **C3** NULL 在唯一索引中的行为（多行 NULL 是否都允许）
      _结果决定 C4 的做法_
- [ ] **C4** 条件唯一的替代方案可用：`active_marker` 列加复合唯一 `(goal_id, active_marker)`，active 行写固定值、非 active 行写自身 id
      _均不可用 → 改为服务端串行化加审计校验，并在文档标注该不变量不由数据库保证_
- [ ] **C5** 外键支持性与级联行为
      _不支持 → 全靠服务端校验；影响可控，归属与无环校验已要求在服务端执行_
- [ ] **C6** CHECK 约束是否生效
      _不支持 → Pydantic 加服务端校验_

### D 事务与并发

- [ ] **D1（红线）** 事务提交与回滚，回滚后无残留
- [ ] **D2** 实测默认隔离级别，不靠推断
      _与协议假设不符 → 按实测值调整第 7 节事务协议_
- [ ] **D3** `SELECT ... FOR UPDATE` 行锁：两连接按同序获取 `user_planning_state` 时正确串行
      _不支持行锁 → 事务协议改为纯条件更新，需重写 `03-data-model.md` 第 7 节_
- [ ] **D4** 条件更新的影响行数语义：`UPDATE ... WHERE revision=?` 在"匹配但值未变化"时返回 1 还是 0；**实测后在连接参数中显式固定，不接受默认值**
      _语义不可固定 → 乐观并发改为"更新后回读校验"，每次多一次查询_
- [ ] **D5** 死锁、锁等待超时、约束冲突三类错误可分别识别
      _无法区分 → 一律按可重试处理，但必须防止把约束冲突误重试_
- [ ] **D6** 记录锁等待超时的默认时长与可配置性

- [ ] **D7** `SKIP LOCKED` 是否支持

## 10. 给接手者

三件事最容易被跳过，但跳过就白做一轮：

1. **D4 是最隐蔽的一条。** MySQL 协议下 UPDATE 的影响行数默认返回"实际改变的行数"而非"匹配的行数"，取决于客户端是否设置 `CLIENT_FOUND_ROWS`。一旦幂等重提时新值等于旧值，影响行数会是 0，`expected_revision` 校验就会**误判为版本冲突**——这是静默的逻辑错误，不会报异常。必须实测并把语义固定在连接参数里，然后在结论表写明固定成了哪一种。

2. **B6 必须在建表设计定稿前做。** utf8mb4 下单列索引有字节上限，按计划列宽建复合唯一索引可能直接失败。放到迁移阶段才发现，就要回头改数据模型和已合并的契约。

3. **不要用"MySQL 兼容"代替实测。** `02-backend-proposal.md` 第 57 段已经写明"连接支持不等于全部迁移操作已兼容"。`SKIP LOCKED`、事务 DDL、部分唯一索引、JSONB 这四项一律按不支持准备替代方案，测出来支持是意外收获。

另外：结论表里的"部分支持"必须写清楚部分在哪，不要合并进"支持"。替代实现一旦被采用，就是后续所有模块的既定前提，含糊描述会让 T05、T07 建立在错误假设上。
