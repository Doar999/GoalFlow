# RFC：改变已确认决策的提案

## 什么时候需要 RFC

设计文档里的结论分三种状态：**已确认**、**建议 / 推荐**、**待定 / 未决**。RFC 用于两类情况：

1. **要偏离一个"已确认"的决策。**
2. **要把一个影响公共契约、数据模型或跨模块行为的"建议 / 待定"收敛成"已确认"。**

只影响单个工作包内部实现的选择**不需要** RFC，记录在该工作包交接卡的"决策与假设"一节即可。判断标准：**别人的代码或页面会不会因为这个选择而改变行为？** 会，就走 RFC。

## 流程

1. 复制 [0000-template.md](0000-template.md) 为 `NNNN-<slug>.md`，编号取当前最大值加一。
2. 提 PR，PR 里只包含这一个 RFC 文件，便于集中讨论。
3. 由对应模块负责人批准；影响产品行为的还需产品决策人确认。
4. 合并后**必须回写**：更新对应的 `docs/product/` 或 `docs/development/` 文档，把状态从"建议 / 待定"改为"已确认"。

第 4 步最容易被漏掉。漏掉它，下一个人的 AI 读到的还是"建议"，还会再猜一次。

## 与设计文档的分工

| 文档 | 承载什么 |
| --- | --- |
| `docs/development/` `docs/product/` | **最终结论**，自包含，不写演进过程 |
| `docs/rfcs/` | **为什么是这个结论**，包含考虑过的替代方案和放弃的理由 |

设计文档正文不要写"原方案是……后来改为……"。那属于 RFC 和 Git 历史。
